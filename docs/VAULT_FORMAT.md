# USNA Secure: Vault Format v1

Normative specification. The reference implementation is `crates/vault-core`; golden vectors in
`crates/vault-core/tests/vectors/` were generated by an independent implementation
(`tools/gen_vectors.py`). If this document and the code disagree, that is a bug to resolve before
release; the format must not be "improvised" in code.

## 0. Conventions
Integers are little-endian. Strings are UTF-8. Hex is lowercase. `||` is concatenation.
All randomness comes from the OS CSPRNG through the `getrandom` crate (the Windows API it calls depends on the resolved crate version; check its documentation when reviewing).

## 1. Primitives (decision 13: no custom crypto)

| Purpose | Primitive | Parameters |
|---|---|---|
| Password KDF | Argon2id v1.3 (RFC 9106) | 32-byte output; m, t, p stored in header; 32-byte salt |
| Key derivation / separation | HKDF-SHA256 (RFC 5869) | salt = vault id; 32-byte outputs |
| Authenticated encryption | XChaCha20-Poly1305 (draft-irtf-cfrg-xchacha) | 256-bit key, 192-bit random nonce, 128-bit tag |
| Hash (tests, manifests) | SHA-256 | |

## 2. Files in a vault
`vault.header` (§3), `vault.db` (§5), `objects/<xx>/<id>.obj` (FILE_FORMAT.md). Transient:
`vault.header.new`, `vault.db.new` (§7).

## 3. Header (`vault.header`), exactly 149 bytes

| Off | Len | Field | Rule |
|---:|---:|---|---|
| 0 | 8 | magic | `55 53 4E 41 56 4C 54 00` ("USNAVLT\0") |
| 8 | 2 | format version | `1`; other values refused, never guessed |
| 10 | 2 | flags | must be `0`; unknown bits refused |
| 12 | 16 | vault id | random, immutable for the life of the vault |
| 28 | 4 | VK generation | starts at 1; +1 per vault-key rotation; `0` invalid |
| 32 | 1 | KDF id | `1` = Argon2id v1.3 |
| 33 | 4 | m cost (KiB) | policy: 19 456 ≤ m ≤ 1 048 576 and m ≥ 8·p |
| 37 | 4 | t cost | policy: 2 ≤ t ≤ 16 |
| 41 | 4 | parallelism | policy: 1 ≤ p ≤ 16 |
| 45 | 32 | KDF salt | random, regenerated on every password change |
| 77 | 24 | wrap nonce | random, regenerated on every header write |
| 101 | 48 | wrapped VK | `XChaCha20-Poly1305(KEK, wrap nonce, AAD, VK)` = 32 B ct + 16 B tag |

(Test builds with the `insecure-test-params` feature relax the m and t floors; release builds refuse
that feature at compile time.)

**Authentication.** `AAD = "USNA Secure v1/vk-wrap" || header[0..77]`. Because bytes 0..77 (magic,
version, flags, vault id, generation, KDF id, all KDF parameters, salt) are AAD of the VK wrap,
changing any of them makes unwrapping fail. There is no separate header MAC. The wrapped VK and nonce
are protected by the AEAD itself. Parsing rejects wrong length (exact 149), magic, version, flags,
KDF id, zero generation and out-of-policy KDF parameters **before** Argon2 runs.

Wrong password and modified header yield the same error by design.

## 4. Key hierarchy (decision 5)

```
Master password (user input)
   │  NFC-normalize (Unicode), UTF-8 bytes, 1..=4096 bytes
   ▼
PDK  = Argon2id(password, salt, m, t, p) → 32 bytes
   ▼
KEK  = HKDF-SHA256(salt = vault_id, ikm = PDK, info = "USNA Secure v1/kek")
   │   wraps ▼ (header, §3)
VK   = 32 random bytes. NEVER derived from the password. Lives only wrapped on disk.
   │
   ├─ K_db       = HKDF(salt = vault_id, ikm = VK, info = "USNA Secure v1/subkey/database"      || gen_le32)
   ├─ K_filewrap = HKDF(salt = vault_id, ikm = VK, info = "USNA Secure v1/subkey/filekey-wrap"  || gen_le32)
   └─ K_manifest = HKDF(salt = vault_id, ikm = VK, info = "USNA Secure v1/subkey/manifest"      || gen_le32)   (reserved; derived on demand when backups land in M3, not held in memory before then)

Per file object:  FileKey = 32 random bytes
   wrapped = nonce(24) || XChaCha20-Poly1305(K_filewrap, nonce,
                 AAD = "USNA Secure v1/filekey" || vault_id || gen_le32 || object_id, FileKey)   (72 bytes)
   (the wrapped key is stored inside the sealed snapshot; file chunks use FileKey directly, see FILE_FORMAT)
```

Domain separation: every AEAD use has its own AAD label (`vk-wrap`, `snapshot`, `filekey`,
`object-chunk`); every derivation has its own HKDF `info`. A key is never used for two purposes.

### Events

| Event | What changes | What does **not** change |
|---|---|---|
| **Password change** | New salt, KDF params, nonce, new KEK; same VK re-wrapped; header rewritten atomically | VK, subkeys, snapshot, all file objects, all wrapped file keys, generation |
| **Vault-key rotation** | New random VK, generation + 1, new subkeys. Snapshot re-sealed (revision + 1). Every wrapped file key re-wrapped (a ~72-byte operation each). New header | Master password, salt, **file keys, file objects (not re-encrypted)** |
| **File replaced** | New object id, new random FileKey, new object written; snapshot updated; old object removed after commit. Keys and nonces are never reused | Other files |
| **File deleted** | Entry removed from snapshot, committed; object file removed afterwards | Other files |
| **Backup restored** | Whole directory state returns to backup time, including the **password in force at backup time** and the generation then | Nothing is merged. Mixed header/snapshot generations are detected (`SnapshotMismatch`) |
| **File-key rotation** (explicit, rare) | Stream-decrypt object → re-encrypt as a new object under a new FileKey → commit → delete old. O(file size) | |

**Honest limits.** VK rotation protects data written after the rotation and old wrapped keys become
unusable under the new generation, but someone who captured an *old* copy of the vault **and** the old
VK can still unwrap old file keys from that old copy and read old objects. If a VK may have leaked,
perform file-key rotation as well. Deleting a file removes its key from the current snapshot, but
old backups and filesystem remnants may still contain the key and the ciphertext, so deletion is
not secure erasure.

## 5. Snapshot container (`vault.db`)

| Off | Len | Field |
|---:|---:|---|
| 0 | 8 | magic `55 53 4E 41 44 42 00 00` ("USNADB\0\0") |
| 8 | 2 | format version `1` |
| 10 | 2 | flags `0` |
| 12 | 16 | vault id |
| 28 | 4 | VK generation |
| 32 | 8 | revision (u64, +1 per save) |
| 40 | 24 | nonce (random per seal) |
| 64 | n | `XChaCha20-Poly1305(K_db, nonce, AAD, padded)` || 16-byte tag |

`AAD = "USNA Secure v1/snapshot" || bytes[0..40]`.
`padded = u64_le(len) || data || zeros`, zero-padded to a multiple of 4096 bytes (minimum 4096).
Total length = 80 + 4096·k for k ≥ 1; anything else is rejected structurally. After authentication the
padding must be all zero and `len` must fit.

Opening requires the vault id and generation in the prefix to equal the unlocked vault's, otherwise
`SnapshotMismatch` (distinct from `AuthenticationFailed` so recovery logic can act on it; these
fields are cleartext and not secret). The container does not interpret `data`; its schema is in
DATA_MODEL.md.

## 6. File objects
Specified in FILE_FORMAT.md: chunked, per-chunk nonce, authenticated index and final flag.

## 7. Atomic commit and crash recovery (decision 5, 6)

Single-file writes: write `X.tmp` → fsync → atomic replace. On Windows the storage layer must use
`MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` (Rust's `std::fs::rename` does not
request write-through; the storage layer is responsible, scheduled for M3).

**Normal save:** write new object files (if any) → seal snapshot with revision + 1 → atomic replace
`vault.db`. Orphaned objects after a crash are garbage-collected by `vault verify`.

**Password change:** atomic replace `vault.header`. Single file, no recovery state.

**VK rotation (two files must change together):**
1. `rotation = vault.begin_vault_key_rotation(password)`; `(rev, plaintext) = rotation.open_old_snapshot(old)`; deserialize; replace **every** wrapped file key with `rotation.rewrap_file_key(..)`; re-serialize; `vault.db.new = rotation.seal_new_snapshot(rev + 1, plaintext)`. (The wrapped keys live inside the snapshot plaintext and are bound to the old generation, so sealing the old plaintext unchanged would lose every file key; there is deliberately no one-shot "reseal" helper.)
2. Write and fsync `vault.db.new`, then `vault.header.new = rotation.new_header_bytes()`.
3. **COMMIT:** atomically rename `vault.header.new → vault.header`.
4. Atomically rename `vault.db.new → vault.db`.
5. `rotation.into_new_vault()`.

**Recovery on open** (read header generation `H` first):

| State found | Action |
|---|---|
| no `.new` files; `vault.db` generation = H | normal |
| `vault.db.new` with generation = H | commit happened; finish step 4 |
| `vault.db.new` with generation = H + 1, header not renamed | roll back: delete `.new` files |
| `vault.header.new` alone | delete it |
| `vault.db` generation ≠ H and no usable `.new` | refuse to open; offer restore from backup (never guess) |

The cleartext generation fields and `inspect_snapshot` exist for exactly this logic. Because every
generation-bound AAD differs, a half-finished state can never decrypt into silently wrong data.

## 8. Backup and restore semantics
A backup is a copy of the vault directory or, preferably, a `.usnabak` archive of the same files (BACKUP_FORMAT.md). It is
already encrypted; possession of it without the password gives the attacker T1, not more. Restoring
replaces state wholesale. Consequences users must be told: (a) old backups open with the password
that was current **when the backup was taken**; (b) restoring an old backup silently loses later
edits; (c) changing a password does not retroactively protect old backups.

## 9. Versioning and compatibility
* `format version` increments for any change that old readers cannot safely interpret.
  Unknown versions and unknown flag bits are refused with a clear error, never partially read.
* Golden files (`tests/vectors/*_v1.bin`) must open with every future release. A change that breaks
  `golden_v1.rs` is a format change and requires a version bump plus a migration.
* Migrations never rewrite in place: write the new form, verify it opens, then swap atomically,
  keeping the old copy until the user confirms.
* Adding a **recovery-key slot** (second KEK wrapping the same VK) will be format v2; the KEK step in
  §4 already provides the domain separation needed for it.

## 10. Reference vectors
`tools/gen_vectors.py` computes Argon2id (m=8 KiB, t=1, p=1), HKDF, XChaCha20-Poly1305 (validated
against the draft's published test vectors) and writes the golden files plus
`src/test_vectors.rs`. The Rust code must reproduce the header byte for byte given the fixed inputs
(`deterministic_create_reproduces_golden_header`).
